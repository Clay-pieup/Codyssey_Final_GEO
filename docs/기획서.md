## 1. 문제 정의

### 1-1. 상황
- 정보 탐색 경로: 검색창 → 대화형 AI(ChatGPT·Claude·Gemini)로 이동 중
- Gartner 예측(2024): 2026년까지 기존 검색엔진 이용량 25% 감소
- AI 답변 = 링크 목록이 아닌 요약 한 덩어리 → 언급되지 않은 브랜드는 노출 기회 없음

### 1-2. 문제
- 중소 브랜드: AI가 자사를 언급하는지 확인할 수단 없음
- 직접 확인 시: AI 여러 개 × 질문 여러 개 × 반복 질의 → 시간 소모
- 같은 질문에도 답이 매번 달라 한두 번 확인으로는 판단 불가

### 1-3. 해결 방향
- 브랜드 정보 입력 → 질문 생성·질의·분석 자동 처리
- 결과: 언급 여부·언급 순서·경쟁사 비교 + 개선 제안
- 진단 직후 결과 메일 자동 발송

## 2. 타겟 사용자

### 2-1. 1차 타겟: 외식업 사장님
- 선정 이유: 업종 고정 → 질문 세트를 외식업 맞춤으로 설계 → 진단 품질 안정
- 소비자 질문 패턴 명확: "OO동 점심 맛집", "OO역 근처 회식 장소" → 지역 + 메뉴 + 상황
- 업종 외 확장: 1차 범위 밖

### 2-2. 사용자 특징
- 매장 운영과 홍보를 직접 병행 → 마케팅에 쓸 시간·인력 부족
- 개발·데이터 분석 지식 없음 → 입력은 상호·지역·메뉴만, 결과는 읽기 쉬운 리포트
- 배달앱·지도앱 리뷰는 관리하지만 AI 답변 노출은 확인 방법 모름

### 2-3. 테스터 확보
- 목표 7~8명 (필수 5명 + 이탈 대비)
- 모집 경로: 당근 광고 → 매장 지역 기반 외식업 사장님 직접 모집
- 수집 항목: 이메일(결과 발송용) → 수집 동의 필수
- 인정 조건 (평가기준 G5): 팀원 제외, 다른 팀 교육생은 외식업 운영자일 때만 인정
- 기록 항목: 가명(T1~), 타깃 해당 근거(업종·매장 지역), 일자, 질문, 응답 → `docs/사용자_피드백_기록.md`

## 3. AI 활용 방식

| 기능 | AI 방식 | 입력 → 출력 |
| --- | --- | --- |
| 질문 생성 | 생성형 AI | 상호·지역·대표 메뉴 → 실제 손님이 물을 법한 질문 10개 |
| 답변 수집 | 생성형 AI | 질문 1개 × 3회 반복 → 답변 원문 |
| 답변 분석 | 생성형 AI | 답변 원문 → 언급 여부·순서·묘사를 정해진 형식(JSON)으로 추출 |
| 추가 질의 판단 | **AI Agent** | 분석 결과 → 질문 도구(함수) 3개 중 호출할 것을 AI가 스스로 선택·실행 |
| 개선 제안 | 생성형 AI | 분석 결과 → 실행 가능한 개선안 3개 |

### 3-1. Agent 범위
- 판단 대상: 추가 질문을 할지, 어떤 종류로 할지
- 상한: 추가 질의 1회(판단 1번, 추가 질문 최대 2개 × 3회 반복) → 최대 호출 +6회로 시간·비용 고정
- 판단 기준: 언급률(가게 이름이 나온 답변 수 ÷ 전체 답변 수) 30% 미만 → 추가 질의 `[확인 필요]` 첫 실측 후 조정
- 구현 방식: 질문 종류 3개를 **각각 별도의 도구(함수)로 만들고**, Gemini 함수 호출 기능으로 AI가 호출할 도구를 고름
  - 직접 지명형 도구 "OO동 ○○식당 어때?" → AI가 가게를 모르는지 / 알지만 추천 안 하는지 구분
  - 경쟁 비교형 도구 "OO동 돈가스집 중 어디가 나아?" → 경쟁 가게 대비 위치
  - 상황 세분형 도구 "OO역 혼밥 점심" → 노출되는 손님 상황 파악
- 이 방식인 이유: 평가기준 G3 Agent 인정 조건 = "LLM이 2개 이상의 도구·함수 중 호출 대상을 스스로 정함"
  - 불인정 사례 "프롬프트 1회 → 응답 출력" → 질문 문장만 AI에게 받아 쓰는 방식은 피함
- 근거 기록: 추가 질문을 한 이유를 결과에 남김 → 인터뷰 설명 자료
- 진단 흐름 예시 (가상 데이터)
  - ▶ [시연 페이지: 진단 과정 직접 실행해 보기](https://claude.ai/artifact/NzMBnhMeMYeXshftv4vL5e) — 언급 적은 가게 / 많은 가게 2가지
  - 문서: [서비스_진단_예시.md](서비스_진단_예시.md)

### 3-2. 측정 신뢰도 장치
- 같은 질문 3회 반복 → 평균값 사용
- 결과 화면에 "AI가 생성한 추정치" 표시
- 웹 검색 사용 (Gemini Grounding with Google Search)
  - 이유: 동네 식당은 AI 학습 자료에 거의 없음 → 검색 없이는 대부분 "언급 없음" → 진단 의미 상실
  - 조건: 유료 등급 전환(카드 등록) → 검색 월 5,000회 무료, 초과 시 1,000회당 $14
  - 예상 사용량: 진단 1회 최대 36회 × 약 100회 = 약 3,600회 → 무료 범위 안
  - 안전장치: Google Cloud 예산 알림·사용 한도 설정 필수 (과금 단위가 문서상 불명확)
- 시간 제한: Vercel 무료 플랜 실행 1회 최대 300초 → 질의 1회 소요 시간 실측 후 동시 호출 여부 결정

## 4. 기술적 접근

### 4-1. 구성
- 화면 → 서버(Python) → Gemini API
- 진단 완료 → 서버가 Make 웹훅 호출 → Make가 결과 메일 즉시 발송
- AI 호출은 파일 1개에 모음 + 결과 형식 통일 → 2차에 ChatGPT·Claude 추가 시 파일만 추가

### 4-2. 필수 기술 요소 (2개)

| 기술 요소 | 이 서비스에서 | 평가기준 G3 인정 조건 대비 |
| --- | --- | --- |
| AI Agent | 질문 도구 3개 중 호출 대상을 AI가 선택·실행 | 인정: "2개 이상 도구·함수 중 호출 대상을 스스로 정함" / 불인정: "프롬프트 1회 → 응답" |
| 자동화 워크플로우 | 진단 완료 이벤트(웹훅) → Make → Gmail 발송 + 구글 시트 기록 | 인정: "이벤트로 시작해 2개 이상 서비스가 사람 개입 없이 이어짐" / 불인정: "버튼 클릭 → API 1회 호출" |

- Make 시나리오 정의 파일(블루프린트 JSON) → 저장소에 보관 (평가기준 경계 사례 안내). 웹훅 주소 등 비밀값은 지우고 보관
- Must 기능에 두 기술 요소가 쓰인 기능 포함 (평가기준 G4)

### 4-3. 기술 스택 선정 이유

| 구분 | 선택 | 버린 대안 | 이유 |
| --- | --- | --- | --- |
| AI | Gemini API (웹 검색 사용) | ChatGPT·Claude 동시 연동 | 1개로 먼저 완성 → 막혀도 서비스 동작. 웹 검색(Grounding) 기능으로 동네 식당까지 검색 |
| 서버 | Python | Node.js | 팀이 과정에서 배운 언어. Vercel에서 Python 함수 실행 가능 |
| 자동화 | Make | n8n | n8n 클라우드 유료. Make 무료 플랜(월 1,000크레딧, 시나리오 2개)으로 충분 |
| 결과 저장 | 구글 시트 (Make가 기록) | 별도 데이터베이스, 저장 안 함 | 코드 없이 저장. 팀 전원이 시트로 열람 |
| 배포 | Vercel | `[작성 필요]` 비교 대상 | push만으로 재배포. 화면과 Python 서버를 한 곳에 배포 |
| 화면 | `[결정 필요]` | | 화면·배포 담당 제안 |

### 4-4. 저장
- 진단 결과 저장: Make → 구글 시트 기록 (메일 발송과 같은 시나리오에 단계 1개 추가)
  - Vercel은 서버에 파일을 계속 남기지 못함 → 외부 저장 필요
  - 코드 추가 없이 저장 → 팀 전원이 시트로 피드백 분석·발표 통계 작성
  - 시트 2개 분리: `진단결과`(상호·지역·질문·답변·분석, 이메일 없음) / `연락처`(이메일·동의 시각)

### 4-5. AI 윤리·개인정보 (평가기준 G7)
- 결과 리포트·메일에 AI 생성 콘텐츠·추정치 명시
- 이메일 수집 전 동의 필수 (항목·목적·보관 기간·거부 권리 고지)
- 보관 기간: 프로젝트 종료 후 30일 → 2026-11-24 `연락처` 시트·Make 실행 기록·발송 메일함에서 파기
- `연락처` 시트 공유 범위: 팀원 3명만
- 테스터 이름·연락처는 저장소에 올리지 않음 → 피드백 기록은 가명 T1, T2 …로 표기
- API 키·테스트 계정 등 비밀 정보는 저장소에 올리지 않음 (노출 시 폐기·재발급 + 심사 반영)

### 4-6. 평가 대비 운영 (서면 평가)
- 평가 방식: 100% 서면. 평가자가 배포 URL로 직접 사용 + 저장소 문서 검토 (발표·질의응답 없음)
- 평가자 접속: 로그인 없는 서비스 → 배포 URL만으로 사용 가능. 테스트 계정이 생기면 저장소가 아닌 제출 시 별도 전달
- 서비스 유지: 제출 후 결과 안내(약 3일)까지 접속 가능 상태 유지
  - Gemini 예산 한도는 서비스가 멈추지 않을 만큼 여유 있게 설정
  - Make 무료 크레딧·검색 무료 횟수 소진 여부를 제출 직전 확인
- 제출 타이밍: 통과 후 재평가 없음 → 필수요건 전부 확인 후 제출
