## 3. G3 기술 요소 인정 기준 대비

| 기술 요소 | 인정 | 불인정 | 우리 설계 |
| --- | --- | --- | --- |
| **AI Agent** ✔ 사용 | LLM이 2개 이상의 도구·함수 중 호출 대상을 스스로 정하거나, 계획 → 실행을 여러 단계로 반복 | 프롬프트 1회 → 응답 출력 | 직접 지명형·경쟁 비교형·상황 세분형 질문을 **각각 함수로 구현**, Gemini 함수 호출로 AI가 선택. 고른 도구와 이유를 리포트에 표시 |
| **자동화 워크플로우** ✔ 사용 | 일정 또는 이벤트로 시작해 2개 이상의 서비스가 사람 개입 없이 이어짐 | 버튼 클릭 → API 1회 호출 | 진단 완료 웹훅(이벤트) → Make → Gmail + 구글 시트 |
| RAG | 질의마다 외부 문서·DB를 검색해 결과를 프롬프트에 넣음 | 고정 텍스트를 프롬프트에 붙임 | 사용 안 함 |
| 멀티모달 AI | 이미지·음성·영상을 모델이 입력·출력으로 처리 | 파일 저장만 하고 모델은 텍스트만 | 사용 안 함 |
| Long-term Memory | 세션이 끝난 뒤에도 사용자별 정보가 저장되어 다음 응답에 반영 | 한 세션 안의 대화 이력 유지 | 사용 안 함 |

- 판정이 애매하면 전문가 평가자 판단에 따름 → **Make 시나리오 정의 파일(블루프린트 JSON)을 저장소에 보관**
- 일정·이벤트로 실행되는 기능(Make)은 구현 현황 표의 확인 방법에 **수동 실행 방법이나 최근 실행 기록 화면**을 적음

### 평가자가 Agent 동작을 반드시 보게 하는 장치

Agent 추가 질의는 언급률 30% 미만일 때만 자동 실행됩니다. 평가자가 유명한 가게를 넣으면 Agent가 작동하지 않아 "기술 요소 미확인"으로 판정될 위험이 있어 두 장치를 둡니다.

| 장치 | 내용 | 평가자가 보는 것 |
| --- | --- | --- |
| ① 확인용 입력 지정 | 명세서 확인 방법에 **실존하지 않는 테스트용 상호**를 지정 → AI가 모르는 가게라 언급률이 항상 0% → 자동 추가 질의 실행 | 어떤 도구를 골랐는지, 왜 골랐는지, 추가 질의 결과 |
| ③ "더 자세히 진단하기" 버튼 | 자동 추가 질의가 실행되지 않은 리포트에 표시. 누르면 언급률과 관계없이 추가 질의 1회 실행 (도구 선택은 동일하게 AI) | 어떤 가게로 진단해도 버튼으로 Agent 동작 확인 |

## 4. 구현 현황 표 작성법 (명세서 마지막)

| 기능명 | Must 여부 | 구현 여부 | 확인 방법 | 기대 결과 |
| --- | --- | --- | --- | --- |
| (예시) 기본 진단 | Must | ✅ | 배포 URL 접속 → 예시 가게 "행복돈까스", 지역 "서울 마포구 망원동", 메뉴 "등심돈까스" 입력 → "진단 시작" 클릭 | 진단이 끝나면 질문 10개별 언급 여부 표와 언급률(%)이 표시된다 |
| (예시) Agent 추가 질의 | Must | ✅ | 상호에 실존하지 않는 테스트용 이름(명세서 작성 시 검색으로 실존 여부 확인), 지역 "서울 마포구 망원동", 메뉴 "등심돈까스" 입력 → "진단 시작" 클릭 | 리포트에 추가 진단 영역이 나타나고, AI가 고른 질문 도구 이름과 이유, 추가 질문 결과가 표시된다 |

- 확인 방법은 **화면·버튼·입력값까지** 적어 평가자가 그대로 따라 할 수 있게 합니다.
- 기대 결과는 **형태로** 적습니다. AI 답은 매번 달라 정확한 숫자를 적으면 3회 중 2회를 맞추기 어렵습니다.

## 5. 제출 절차와 이후 흐름

1. 6장 최종 점검을 마친다
2. 코디세이 플랫폼 → 파이널 프로젝트 미션 → GitHub 저장소 연결로 제출
3. 테스트 계정이 생겼다면 저장소가 아닌 제출 시 별도 전달 (현재 로그인 없음 → 해당 없음)
4. 결과 안내: 접수 후 약 3일 이내. **그때까지 서비스 접속 유지**
5. 미충족 → 안내된 항목 보완 후 원할 때 재제출 / 추가 요청 → 보완 자료만 제출 / 통과 → 재평가 없음 (그 시점 결과물로 확정)

## 6. 제출 직전 최종 점검

통과 후에는 재평가가 없으므로 아래를 모두 확인한 뒤 제출합니다.

- [ ] **구동**: 시크릿 창에서 배포 URL 접속 → 명세서 구현 현황 표의 Must 기능을 확인 방법대로 **각 3회** 실행 → 2회 이상 기대 결과
- [ ] **Agent 확인**: 테스트용 상호로 자동 추가 질의 1회, 다른 가게로 "더 자세히 진단하기" 버튼 1회 확인
- [ ] **Make**: 진단 후 메일 수신, 구글 시트 기록, Make 실행 기록 화면 확인
- [ ] **비밀값 검색**: 저장소 전체(커밋 이력 포함)에서 API 키, 웹훅 주소, 테스터 실명·전화번호·이메일이 없는지 확인
- [ ] **블루프린트**: `automation/make_scenario.json`의 웹훅 주소·이메일이 `REMOVED`로 바뀌어 있는지 확인
- [ ] **링크**: README와 docs 문서의 모든 링크를 눌러 열리는지 확인
- [ ] **문서 위치**: 기획서·명세서·피드백 기록·발표 자료(PDF)가 `docs/`에 있는지 확인
- [ ] **기여 기록**: README 역할 표에 3명 모두 본인 작성 기여 요약 + 대표 커밋·PR·문서 링크
- [ ] **한도 잔량**: Gemini 선불 잔액(AI Studio → 결제), 웹 검색 무료 횟수, Make 무료 크레딧이 결과 안내까지 버틸 만큼 남았는지 확인
  - Gemini 잔액이 0이 되면 모든 키가 즉시 멈춤 → 진단 Must 실패. 자동 충전은 꺼 두었으므로 부족하면 수동으로 추가 충전
- [ ] **시연 페이지**: README의 시연 페이지 링크를 "가상 데이터 프로토타입"으로 명확히 표시했는지, 또는 내렸는지 확인

## 8. 이것만은 꼭

- 결과 안내 전까지 서비스 접속 유지: API 한도 소진, 무료 호스팅 절전 모드 주의 (Vercel 무료 플랜은 요청이 올 때 실행되는 방식이라 절전으로 멈추지는 않음)
- API 키 같은 비밀 정보와 테스터 개인정보는 저장소에 절대 올리지 않음
- 서면 심사라 평가자가 알아야 할 내용은 **모두 제출물 안에** 적음
- 통과 후 재평가 없음 → 제출 타이밍 신중하게
