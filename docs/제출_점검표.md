**판정**
- 단순 자료 누락(기여 기록, AI 표기 문구, 문서 위치·형식, 발표 자료, 진행 기록, 타깃 근거·가명 처리) → 추가 요청 → 보완 자료만 제출
- 접속·구동 불가, 기술 요소 미달, Must 기능 미구현, 테스터 5명 미달, 버전 이력 없음, 동의 절차 없음 → 미충족 → 보완 후 재평가

## 3. G3 기술 요소 인정 기준 대비

| 기술 요소 | 인정 | 불인정 | 우리 설계 |
| --- | --- | --- | --- |
| **AI Agent** ✔ 사용 | LLM이 2개 이상의 도구·함수 중 호출 대상을 스스로 정하거나, 계획 → 실행을 여러 단계로 반복 | 프롬프트 1회 → 응답 출력 | 직접 지명형·경쟁 비교형·상황 세분형 질문을 **각각 함수로 구현**, Gemini 함수 호출로 AI가 선택 |
| **자동화 워크플로우** ✔ 사용 | 일정 또는 이벤트로 시작해 2개 이상의 서비스가 사람 개입 없이 이어짐 | 버튼 클릭 → API 1회 호출 | 진단 완료 웹훅(이벤트) → Make → Gmail + 구글 시트 |
| RAG | 질의마다 외부 문서·DB를 검색해 결과를 프롬프트에 넣음 | 고정 텍스트를 프롬프트에 붙임 | 사용 안 함 |
| 멀티모달 AI | 이미지·음성·영상을 모델이 입력·출력으로 처리 | 파일 저장만 하고 모델은 텍스트만 | 사용 안 함 |
| Long-term Memory | 세션이 끝난 뒤에도 사용자별 정보가 저장되어 다음 응답에 반영 | 한 세션 안의 대화 이력 유지 | 사용 안 함 |

- 판정이 애매하면 전문가 평가자 판단에 따름 → **Make 시나리오 정의 파일(블루프린트 JSON)을 저장소에 보관**
- 일정·이벤트로 실행되는 기능(Make)은 구현 현황 표의 확인 방법에 **수동 실행 방법이나 최근 실행 기록 화면**을 적음

## 4. 구현 현황 표 작성법 (명세서 마지막)

| 기능명 | Must 여부 | 구현 여부 | 확인 방법 | 기대 결과 |
| --- | --- | --- | --- | --- |
| (예시) 기본 진단 | Must | ✅ | 배포 URL 접속 → 예시 가게 "행복돈까스", 지역 "서울 마포구 망원동", 메뉴 "등심돈까스" 입력 → "진단 시작" 클릭 | 진단이 끝나면 질문 10개별 언급 여부 표와 언급률(%)이 표시된다 |

- 확인 방법은 **화면·버튼·입력값까지** 적어 평가자가 그대로 따라 할 수 있게 합니다.
- 기대 결과는 **형태로** 적습니다. AI 답은 매번 달라 정확한 숫자를 적으면 3회 중 2회를 맞추기 어렵습니다.

## 5. 이것만은 꼭

- 결과 안내 전까지 서비스 접속 유지: API 한도 소진, 무료 호스팅 절전 모드 주의
- API 키 같은 비밀 정보와 테스터 개인정보는 저장소에 절대 올리지 않음
- 서면 심사라 평가자가 알아야 할 내용은 **모두 제출물 안에** 적음
- 통과 후 재평가 없음 → 제출 타이밍 신중하게
