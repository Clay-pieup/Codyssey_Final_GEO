### 2-1. AI Agent: 질문 도구 3개를 함수로 정의하고 Gemini가 선택

**상황**
- 기본 질문 10개 × 3회만으로는 가게가 **왜** 안 나오는지 모름. AI가 이 가게를 아예 모르는지, 알지만 다른 가게를 추천하는지, 특정 상황에서만 안 나오는지 구분이 필요
- 평가기준 G3 Agent 인정 조건: "LLM이 2개 이상의 도구·함수 중 호출 대상을 스스로 정함" / 불인정: "프롬프트 1회 → 응답 출력"

**고민한 대안**

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| 버림: 규칙으로 도구 선택 (예: 언급 0%면 직접 지명형) | 매번 같은 결과 | AI가 고르지 않으므로 G3 불인정, 결과를 보고 판단하지 못함 |
| 버림: 추가 질문 문장만 AI에게 받기 | 구현이 간단 | "프롬프트 1회 → 응답"이라 G3 불인정 |
| 버림: 여러 단계 반복 (결과 보고 또 질문) | 깊은 분석 | 호출·시간이 끝없이 늘어 Vercel 300초 위험, 비용 예측 불가 |
| ✅ **선택**: 도구 3개를 함수로 정의 + Gemini 함수 호출로 선택, 실행은 코드 | G3 충족, AI는 고르기만 하고 코드가 검사·실행해 안전 | 언급률이 중간인 가게는 선택이 회차마다 달라질 수 있음 |

**결정 내용**
- 도구: 직접 지명형("망원동 ○○ 어때?"), 경쟁 비교형("망원동 돈까스집 중 어디가 나아?"), 상황 세분형("망원역 혼밥 점심")
- Gemini가 기본 진단 요약을 보고 1~2개를 골라 질문 문장과 고른 이유(`why`)를 채움 → 코드가 규칙 검사(지역 포함, 상호 포함 여부, 중복) → 통과한 질문만 3회씩 실행
- 추가 질의는 진단 1회당 1번 (판단 1번, 질문 최대 2개 × 3회 = 최대 +6회)

**근거 데이터와 결과**
- 10/19 행복돈까스(언급률 0%): AI가 직접 지명형 선택, 이유 "멘션율이 0%로 AI가 가게를 전혀 언급하지 않아 존재 여부와 인지 상태를 확인"
- 10/20 명동교자(90%): 상황형 3개 중 2개만 언급 → 상황 세분형 선택 / 경쟁 가게(미성옥·신선설농탕)가 함께 나옴 → 경쟁 비교형 선택
- 10/22 테스트 상호 2곳: 3회 모두 언급률 0% → 직접 지명형 선택 (판단이 매번 같음)
- 코드: `ai/agent.py` `TOOLS`·`run_agent()`, `ai/gemini_client.py` `choose_tools()` / 커밋 `7297da3`

### 2-2. 웹 검색(Grounding) 사용

**상황**
- 동네 식당은 AI가 학습한 자료에 거의 없음 (기획서 3-2)
- 웹 검색은 비용이 들고(유료 키 필요) 호출 시간이 늘어남

**고민한 대안**

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| 버림: 웹 검색 끔 | 무료 키로 가능, 빠름 | AI가 모르는 가게를 아는 척함 → 진단 결과를 믿을 수 없음 |
| ✅ **선택**: 웹 검색 켬 (배포는 유료 키) | 실제 웹 정보를 근거로 답, 출처 확인 가능 | 유료 키 필요, 시간 증가 |

**근거 데이터**

| 날짜 | 조건 | 결과 |
| --- | --- | --- |
| 10/19 | 무료 키 · 웹 검색 켬 | 12회 모두 429 (무료 키에는 웹 검색 할당량 없음) → 배포는 유료 키로 결정 |
| 10/19 | 웹 검색 끔 · 가상 가게 "행복돈까스" 직접 지명형 | "노포의 감성과 가성비로 사랑받는 숨은 맛집"이라고 **지어낸 답** |
| 10/22 | 유료 키 · 웹 검색 켬 · 가상 가게 2곳 | 기본 질문 30개 × 3회 모두 **언급 0회** (아는 척 안 함) |
| 10/23 | 배포 환경 · 웹 검색 켬 · 명동교자 | 19.3초, 출처 152개 (블로그 57, SNS·영상 36, 지도·리뷰 16 …) |

- 결과: 웹 검색이 진단 신뢰도의 핵심이라는 걸 실험으로 확인. 부가로 "Gemini는 네이버 블로그보다 티스토리·유튜브를 많이 참고한다"는 사장님용 조언 근거도 얻음

### 2-3. 손님 질문 10개를 4가지 유형으로 생성, 규칙은 코드가 검사

**상황**
- 사장님은 손님이 AI에게 어떻게 묻는지 모름. 질문이 매번 달라지면 결과를 비교할 수 없음

**고민한 대안**

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| 버림: 사장님이 질문 직접 입력 | 원하는 질문 확인 | 입력 부담, 손님 시각이 아닌 사장님 시각 질문 |
| 버림: 고정 질문 템플릿 ("○○동 ○○ 맛집") | 매번 같음 | 업종·메뉴마다 말투가 어색함 |
| 버림: AI가 자유롭게 생성 | 자연스러움 | 상호가 질문에 들어가거나 지역이 빠져도 알 수 없음 |
| ✅ **선택**: 4가지 유형 개수 고정 + AI가 문장 생성 + 코드가 규칙 검사 | 자연스러우면서 규칙은 지켜짐, 유형별 언급률로 약점이 보임 | 규칙 실패 시 재생성 비용 |

**결정 내용**
- 유형: 지역 일반형 2 · 메뉴형 3 · 상황형 3 · 조건형 2 (실제 손님 질문 패턴 "지역 + 메뉴 + 상황")

**근거 데이터와 결과**

### 2-5. "더 자세히 진단하기": 화면이 1차 리포트를 다시 보냄

**상황**
- 언급률 30% 이상이면 자동 Agent가 없음 → 평가자가 실존 가게로 진단하면 Agent를 볼 수 없음 (팀 결정: 버튼 추가)
- Vercel 서버는 요청마다 새로 시작해 1차 결과를 기억하지 못함

**고민한 대안**

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| 버림: 버튼을 누르면 처음부터 다시 진단 | 구현 간단 | 호출 51회를 또 씀, 질문이 바뀌어 1차 결과와 이어지지 않음 |
| 버림: 1차 결과를 구글 시트·서버 파일에 저장 | 서버가 기억 | Vercel은 파일을 못 남김, 시트를 읽으려면 Make 시나리오 추가 |
| ✅ **선택**: 화면이 가진 1차 리포트를 다시 보내면 Agent만 실행 (`run_more`) | 추가 호출 최대 10회, 저장소 불필요 | 서버가 "1회만"을 완전히 막을 수 없음 → 화면 버튼 비활성화로 보완 |

- 보완: 이미 추가 질의를 한 리포트, 깨진 리포트, 실패 리포트는 실행하지 않고 안내 문장 반환. 자동 Agent가 429로 실패한 리포트도 버튼으로 다시 시도 가능
- 결과: 10/20 명동교자 3회 모두 버튼으로 Agent 실행 성공, 10/22 배포 환경 13초 (팀장 확인)
- 코드: `ai/diagnosis.py` `run_more()`, `ai/agent.py` `run_agent(force=True)` / 커밋 `3d32f31`, `7aa42c6`

### 3-1. AI가 하는 일 한눈에

- **핵심 문장**: AI는 "만들고, 읽고, 고르고, 제안"하고, 규칙과 숫자는 코드가 지킵니다
- **본문 (흐름도)**

```
가게 정보 입력 ─▶ ① 질문 10개 생성 (AI) ─▶ ② 질문마다 3회 질의 (AI + 웹 검색)
   ─▶ ③ 답변 분석: 언급·순위·묘사 (AI) ─▶ ④ 언급률 집계 (코드)
   ─▶ ⑤ 추가 질문 고르기 (AI Agent) ─▶ ⑥ 개선 제안 3개 (AI) ─▶ 리포트 · 메일
```

| AI가 맡은 일 | 코드가 지키는 일 |
| --- | --- |
| 손님 말투의 질문 만들기 | 질문 개수·상호 미포함·지역 포함 검사 |
| 답변에서 가게 언급·묘사 찾기 | 언급률 계산 (분모는 정상 답변만) |
| 추가로 물을 질문 종류 고르기 | 고른 질문의 규칙 검사·실행, 1회 상한 |
| 개선 제안 쓰기 | 진단 결과 안의 숫자만 근거로 쓰게 지시 |

- **시각 자료**: 위 흐름도를 가로 화살표 도식으로. AI 단계는 파란색, 코드 단계는 회색
- **근거 위치**: `AI_활용명세.md` 0~1장

### 3-2. 손님처럼 묻는 질문 10개

- **핵심 문장**: 손님은 "지역 + 메뉴 + 상황"으로 묻습니다. 그래서 질문을 4가지 유형으로 나눴습니다
- **본문**

| 유형 | 개수 | 예시 (가상 가게 "행복돈까스", 망원동) | 알 수 있는 것 |
| --- | :-: | --- | --- |
| 지역 일반형 | 2 | 망원동 점심 맛집 추천해줘 | 동네 대표 가게로 나오는가 |
| 메뉴형 | 3 | 망원동 치즈돈까스 맛있는 곳 | 대표 메뉴로 알려져 있는가 |
| 상황형 | 3 | 망원역 혼밥하기 좋은 곳 | 어떤 손님 상황에서 추천되는가 |
| 조건형 | 2 | 망원동 주차 되는 식당 | 가성비·주차 같은 조건에서 나오는가 |

- 유형별 언급률을 따로 보면 "메뉴형에서만 0%"처럼 **고칠 곳이 보임** → 개선 제안의 근거
- 문장은 AI가 만들고, 규칙은 코드가 검사 → 어기면 틀린 점을 알려 주고 최대 3번 다시 생성
- 실측에서 얻은 설계: 우래옥을 "주교동"으로 물으면 6번 모두 미언급, 손님은 "을지로"로 부름 → **가까운 역 입력** 추가
- **시각 자료**: 4가지 유형 카드 + 화면 `1019_questions_success.png`(질문 10개 생성), `1019_questions_check_fail.png`(규칙 검사가 오류를 잡음)
- **근거 위치**: 2장 2-3, `질문세트_측정기준.md`

### 3-3. 왜 웹 검색을 켰나

- **핵심 문장**: 웹 검색 없이는 AI가 모르는 가게도 아는 척합니다
- **본문 (실험 비교)**

| | 웹 검색 끔 | 웹 검색 켬 |
| --- | --- | --- |
| 가상 가게에 대한 AI 답 | "노포의 감성과 가성비로 사랑받는 숨은 맛집" (**지어냄**, 10/19) | 기본 질문 30개 × 3회 **언급 0회** (10/22) |
| 근거 출처 | 없음 | 진단 1회 출처 152개 (10/23 배포) |
| 비용 | 무료 키 가능 | 유료 키 필요 (무료 키는 웹 검색 할당량 0, 10/19 확인) |

- 결론: 진단의 신뢰도는 웹 검색에 달려 있음 → 배포는 유료 키 + 웹 검색 켬
- **시각 자료**: 좌우 비교 카드. 왼쪽에 지어낸 답 문장 인용, 오른쪽에 "0/30 · 0/30 · 0/30"
- **근거 위치**: 2장 2-2, `작업기록/AI.md` 10/19·10/22

### 3-4. AI Agent, 다음 질문을 AI가 고른다

- **핵심 문장**: 질문 도구 3개를 함수로 주면, Gemini가 진단 결과를 보고 무엇을 물을지 스스로 고릅니다
- **본문**

| 도구 (함수) | 예시 질문 | 알아내는 것 |
| --- | --- | --- |
| 직접 지명형 | 망원동 행복돈까스 어때? | AI가 가게를 아예 모르나, 알지만 추천을 안 하나 |
| 경쟁 비교형 | 망원동 돈까스집 중 어디가 나아? | 함께 나온 경쟁 가게와 비교한 위치 |
| 상황 세분형 | 망원역 혼밥 점심 어디가 좋아? | 어떤 상황에서 노출되고 안 되나 |

- **AI가 실제로 고른 예**
  - 언급률 0% → 직접 지명형. 이유: "멘션율이 0%로 … 존재 여부와 인지 상태를 확인하기 위해" (10/19)
  - 명동교자, 상황형 3개 중 2개만 언급 → 상황 세분형 / 미성옥·신선설농탕이 함께 나옴 → 경쟁 비교형 (10/20)
- **G3 인정 조건 대비**: "LLM이 2개 이상 도구 중 호출 대상을 스스로 정함" ✅ / 불인정 "프롬프트 1회 → 응답"을 피하려고 질문 문장만 받는 방식은 버림
- 안전장치: AI는 **고르기만**, 실행은 코드 → 지역이 빠진 질문 등은 실행 전에 걸러지고 이유도 기록 / 진단 1회당 추가 질의 1번
- **시각 자료**: "진단 결과 → Gemini(함수 3개 중 선택) → 코드 검사 → 실행 → 리포트에 이유 기록" 도식 + 화면 `1019_agent_direct_name.png`
- **근거 위치**: 2장 2-1, `ai/agent.py` `TOOLS`, `ai/gemini_client.py` `choose_tools()`

### 3-5. 어떤 가게로도 Agent를 볼 수 있게

- **핵심 문장**: 언급이 적으면 자동으로, 많으면 버튼으로 Agent가 동작합니다
- **본문**

| 경로 | 언제 | 평가자 입력 예 | 확인 결과 |
| --- | --- | --- | --- |
| 자동 | 언급률 30% 미만 | 초록별돈까스 망원점 / 서울 마포구 망원동 / 등심돈까스 | 3회 모두 0% → 자동 Agent (10/22) |
| 버튼 "더 자세히 진단하기" | 자동 Agent 결과가 없을 때 | 명동교자 / 서울 중구 명동 / 칼국수, 만두 → 버튼 클릭 | 3회 모두 버튼으로 Agent 실행 (10/20), 배포 13초 |

- 서버는 요청마다 새로 시작해 1차 결과를 기억 못 함 → 화면이 1차 리포트를 다시 보내면 Agent만 실행 (추가 호출 최대 10회)
- 평가자용 상호는 웹 검색·지도앱으로 같은 이름 가게가 없음을 확인. "행복돈까스"는 실제 같은 이름 가게가 있어 제외
- **시각 자료**: 두 갈래 흐름도 (언급률 < 30% → 자동 / ≥ 30% → 버튼) + 화면 `1022_testname_dalmuri.png`
- **근거 위치**: 2장 2-5, `AI_인수인계.md` 6장

### 3-6. 빠르고 예측 가능하게

- **핵심 문장**: 진단 1회 호출 수를 51회로 고정하고, 빠른 모델과 동시 호출로 20초대에 끝냅니다
- **본문**

| 단계 | 호출 수 |
| --- | :-: |
| 질문 생성 | 1 |
| 질의 (질문 10개 × 3회, 웹 검색) | 30 |
| 답변 분석 (질문 단위로 묶음, 30 → 10) | 10 |
| Agent 선택 + 추가 질의 + 추가 분석 | 1 + 6 + 2 |
| 개선 제안 | 1 |
| **합계** | **최대 51** |

| 모델 | 진단 1회 (같은 조건) |
| --- | :-: |
| gemini-3.8-flash | 177~191초 |
| **gemini-3.5-flash-lite (선택)** | 28~32초, 배포 19~23초 |

- 같은 오류(모델 이름·키 오류)는 재시도하지 않고, 분당 한도는 기다렸다가 다시 시도 → 비용과 시간이 새지 않음
- **시각 자료**: 호출 수 막대(단계별 누적) + 두 모델 시간 비교 막대
- **근거 위치**: `AI_활용명세.md` 3-1, 2장 2-4·2-7

### 3-7. 같은 입력 3번, 모두 통과

- **핵심 문장**: Must 기능을 같은 입력으로 3번씩, 4곳에서 돌려 모두 통과했습니다
- **본문**

| 가게 | 조건 | 언급률 (1·2·3회) | Agent | Must ① | Must ② |
| --- | --- | :-: | :-: | :-: | :-: |
| 명동교자 (실존) | 웹 검색 끔 | 90 · 100 · 90% | 버튼 | 3/3 | 3/3 |
| 행복돈까스 (가상) | 웹 검색 끔 | 0 · 0 · 0% | 자동 | 3/3 | 3/3 |
| 초록별돈까스 (평가자용) | 웹 검색 켬 | 0 · 0 · 0% | 자동 | 3/3 | 3/3 |
| 달무리칼국수 (평가자용) | 웹 검색 켬 | 0 · 0 · 0% | 자동 | 3/3 | 3/3 |

- 판정을 코드로 고정한 점검 스크립트(`ai/quality_check.py`) → 누구나 다시 돌릴 수 있음
- 언급률이 회차마다 거의 같음 (90·100·90%) → 반복 3회 평균이 안정적
- **시각 자료**: 위 표 + 화면 `1020_quality_myeongdong.png`, `1022_testname_chorokbyeol.png`
- **근거 위치**: `작업기록/품질점검.md`, `AI_활용명세.md` 5장

### 3-8. 진단이 알려 준 것

- **핵심 문장**: AI는 네이버 블로그보다 티스토리·유튜브를 근거로 가게를 소개합니다
- **본문 (배포 환경, 명동교자, 출처 152개)**

### 3-9. AI의 한계를 숨기지 않는다 (G7)

- **핵심 문장**: AI 결과는 추정치라고 밝히고, 판단 이유와 출처를 함께 보여 줍니다
- **본문**

| 한계 | 우리가 한 일 |
| --- | --- |
| 실제 ChatGPT·Gemini 앱 답과 다를 수 있음 | 모든 리포트에 "AI가 생성한 추정치입니다" 문구(`notice`) 포함, Make로 메일에도 같은 문구 전달 |
| 같은 질문에도 답이 매번 다름 | 질문마다 3회 반복, 언급률 분모를 함께 표시, 정상 답변 2/3 미만이면 "신뢰도 낮음" |
| AI가 모르는 가게를 아는 척할 수 있음 | 웹 검색 켬으로 운영, 한계를 문서에 기록 |
| AI가 근거 없는 약속을 할 수 있음 | 개선 제안은 진단 결과 안의 숫자로만 근거, "노출 30% 상승" 같은 약속 금지 |
| AI 판단이 블랙박스 | Agent가 고른 이유, 규칙 검사에서 뺀 질문, 출처를 리포트 데이터에 기록 (화면 표시용) |
| 개인정보 | AI에는 가게 정보만 전달, 이메일은 넘기지 않음 |

- **시각 자료**: 리포트 화면에서 "추정치 안내 / 고른 이유 / 출처"가 보이는 곳 (화면·메일 표시 여부는 화면·Make 담당 확인 후 팀장이 맞춤)
- **근거 위치**: `AI_활용명세.md` 4장

### 3-10. 만들 때 참고

- 슬라이드 1장에 핵심 문장 1개. 숫자는 크게, 설명은 표로
- 화면 캡처는 작게 넣고 아래에 "날짜 · 무엇을 확인한 화면인지" 한 줄
- 예시 질문·가게 이름은 가상 데이터임을 슬라이드 아래에 표시 (명동교자·우래옥은 실존 가게로 실측에만 사용)
- 팀 발표 자료의 다른 파트(문제 정의, 화면, 자동화, 피드백)와 이어지도록 슬라이드 1의 흐름도를 전체 구조도와 맞춤
